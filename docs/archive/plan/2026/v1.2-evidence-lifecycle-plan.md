# v1.2 增量核验与证据生命周期计划

## 基线与目标

本计划以 GitHub `main` 提交 `756997998051de22746fcd7bf9b211129697de0d` 为实施基线，在保留 v1.1 CLI、来源 Adapter、相关性过滤和运维脚本的前提下，补齐跨运行增量核验、受控证据解析与证据复核生命周期。

v1.2 不降低 `verified` 门槛，不允许媒体转述、搜索摘要、模型输出或相似域名成为证据，也不允许 Codex 扩大程序配置的官方域名和 GitHub 组织边界。

## 交付范围

### 1. 受控证据解析

相关 discovery 候选按固定顺序处理：

1. 候选自身的官方 URL；
2. 候选页面中首个明确的第一方链接；
3. Codex 给出的结构化建议。

每个证据 URL 都必须由程序重新抓取，并通过精确 HTTPS host、精确 GitHub 组织、同域重定向、可见正文逐字摘录、发布日期和规范化正文哈希校验。候选页发生跨域重定向时立即停止，不继续交给模型；搜索页、媒体页、伪造子域名和近似组织名不能产生 `verified`。

### 2. Pending 增量核验

首次核验因可重试原因失败时，条目写入独立于 `DedupState` 的 `PendingVerificationState`，记录尝试次数、最后原因、下次重试、上限和 TTL。

- 新运行先执行正常相关性过滤和跨运行去重，再合并到期 pending。
- 即使本次候选已命中去重，到期 pending 仍可重试。
- 成功核验后删除 pending；次数上限和 TTL 分别记录稳定终止原因。
- 来源整体失败时不执行 pending 核验，也不改变 pending 状态。

### 3. 原子状态事务

一次成功运行的历史 RunReport、`latest.json`、dedup 和 pending 采用同一提交事务：全部先写同目录临时文件并 `fsync`，再替换目标。任一步骤失败时恢复提交前内容并删除本次历史 run。

运行状态为 `failed` 时仍保存失败历史 run，但不覆盖 latest，也不提交 dedup 或 pending 的演进结果。

### 4. 证据生命周期

首次核验继续要求正文哈希完全一致。对既有证据复核时：

- 哈希未变化：`current`；
- 整页变化，但原摘录、日期和安全边界仍成立：`changed_supporting`，保存前一哈希并输出警告；
- 摘录消失、日期不匹配、不可访问、域名或重定向异常：`failed`，条目降级为 `unverified` 并清除过期主证据。

### 5. RunReport 1.2

RunReport 新输出使用 schema `1.2`，以 additive minor 方式增加：

- `verification_retry`；
- `verification_stats`；
- `evidence_reviews`；
- 证据的重定向、日期、哈希和生命周期字段。

读取器继续接受 `1.0` 和 `1.1`；只有 `1.2` 报告强制完整严格证据门槛。`validate --check-evidence` 将仍具支持事实的正文漂移报告为 warning，而不是误判为证据失效。

## 非目标

- 不自动安装、修改或运行真实 launchd。
- 不提交 `output/`、`state/` 或 `logs/` 运行数据。
- 不把 mock、连接器读取或模型回答替代真实生产 Codex G6-V。
- 不修改 v1.1 已验证的 Source Adapter 边界，除非修复本计划直接暴露的兼容问题。

## 真实环境交接

真实环境执行步骤、隔离目录、命令、断言、产物和结论口径统一维护在 [v1.2 真实环境验收与交接清单](../../testing/2026/v1.2-real-environment-acceptance.md)。实际环境开发或验收必须从该清单开始，并在执行时记录真实 HEAD、日期、环境边界和脱敏后的结果。

需要实际环境完成的项目只有：

- **G6-S：真实来源。** 全来源或受影响来源 live probe，记录稳定/实验来源的真实状态和限制。

本交接不要求也不允许操作真实 launchd。所有运行数据和秘密必须留在隔离环境，验收记录只提交脱敏摘要。
