# mynews v1.5 扩展来源与安全交接计划

## 基线与目标

本计划从实际 `main` HEAD `ac75d0e` 开始，实施分支固定为
`codex/v1.5-expanded-sources-handoff`。v1.4 外部 SourcePlugin entry-point、显式加载、
严格协议校验、结构化失败和 Store 保护已经离线实现，本计划不重新设计该边界。

v1.5 交付已合入 `main` 提交 `43ff00c`。后续阶段不得从本实施分支续做；必须先确认
`main` 包含本提交，再从最新 `main` HEAD 创建新的 `codex/<phase>` 分支。

目标是在不改变默认采集的前提下，提供一个显式扩展模式：一次运行同时采集既有
built-in 来源与从 `newsFromAI` 核对得到的额外 RSS/Atom 来源，并增加人工检查清单、
可分享输出隐私门禁和 report 原子写入。新增来源仍只能产生候选，任何 `verified`
结论继续经过既有第一方证据与程序二次校验。

## 已确认的产品决定

- `uv run mynews collect --days 7` 与普通 `probe` 保持 v1.4 行为，只使用 built-in。
- 新增 `--with-plugin <id>` 表示“保留 built-in 选择并追加显式插件”；既有
  `--plugin <id>` 继续表示“只运行显式插件”，语义不得改变。
- 新增来源包位于 `plugins/newsfromai-source-pack/`，是独立 Python 分发包；它不进入
  mynews 主 wheel、不成为生产依赖，只有显式安装后才会被 entry-point 发现。
- `scripts/collect-expanded.sh` 固定选择本计划列出的 15 个插件来源，并把日期、核验和
  `--digest` 参数安全透传给现有 `scripts/collect.sh`。
- SQLite、发布台账、自动发布、正文生产、PPT、小红书、Canva 和真实 launchd
  变更均不属于 v1.5。

## 核心接口与处理规则

1. 将现有通用 RSS/Atom Adapter 提升为稳定的外部插件辅助接口；继续复用共享 HTTP、
   请求时间窗、官方域名检查和结构化错误，不增加 feedparser 等生产依赖。
2. `normalize_source_role` 兼容新增 `research`、`incident`、`benchmark`：
   `research` 与 `incident` 可作为官方候选，`discovery` 与 `benchmark` 都执行确定性
   AI/科技相关性筛选；角色不改变 `verified` 门槛。
3. collect/probe 新增可重复的 `--with-plugin`：
   - 未指定 `--source` 时，选择全部 built-in 加显式插件；
   - 指定 `--source` 时，选择指定 built-in 加显式插件；
   - `--plugin` 不得与 `--source` 或 `--with-plugin` 混用；
   - `requested_range.source_ids` 记录实际选择的 built-in 与插件 source_id。
4. 插件发现、加载、ID 或协议校验失败发生在流水线前，不修改任何 Store 文件；来源
   运行时失败继续形成独立 SourceResult，其他来源仍执行，整体状态沿用现有规则。
5. 插件包未安装时，默认 collect/probe 不受影响；扩展脚本必须以结构化
   `plugin_not_found` 失败，不允许悄悄退化为仅采集 built-in。

## 人工检查与安全输出

- 新增 `config/manual-watchlist.json` 的 1.0 Pydantic 契约，每项固定包含
  `id`、`name`、`url`、`role`、`note`；只纳入尚无 built-in 或本计划插件、且来源目录
  标为 stable/adapter/manual 的官方页面。
- 新增 `mynews watchlist --file config/manual-watchlist.json [--out PATH]`；它只验证并
  渲染确定性 Markdown，不访问网络、不创建 Candidate、不调用 Codex、不修改 Store。
- report、digest、watchlist 的人类可分享输出统一检查个人绝对路径、疑似密钥赋值和
  token/signature 等敏感 URL 查询参数；失败只返回字段路径和原因，不回显敏感值。
- report 文件输出使用同目录临时文件、`flush`、`fsync`、`os.replace`；失败时保留旧
  文件并清理临时文件。Digest 继续使用已有三文件事务，不顺带重构 JSON Store。

## 实施阶段

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| P1 | 文档基线、角色扩展、通用 Feed 插件辅助接口 | 旧角色、Qwen Feed、SourcePlugin 1.0 和默认 registry 回归通过 |
| P2 | 独立来源包及 15 个 entry-point | 每个来源有 metadata、RSS/Atom fixture、域名/组织和失败测试 |
| P3 | `--with-plugin` 与扩展采集脚本 | 默认来源选择、Schema 和确定性 fixture 序列化兼容；扩展采集同时包含两类来源 |
| P4 | watchlist、输出隐私门禁与 report 原子写入 | 敏感内容不泄漏；失败不覆盖现有文件或 latest |
| P5 | 离线门禁与文档同步 | docs、Ruff、Mypy、相关测试、全量测试和中文 help 全部通过 |
| P6 | 真实来源与隔离七天验收 | 逐来源 G6-S + 扩展 collect/validate/digest 证据完整记录 |

P1–P5 通过后能力最高为 Implemented。P6 必须逐来源记录 `healthy`、`blocked` 或
`failed`；只有真实 probe 至少解析一条有效记录的来源才能单独标为 Verified。
experimental 来源被阻断可以如实保留为 BLOCKED，但不得伪装为健康。

## 验证命令与验收判定

实施时先运行最小相关测试，再执行：

```bash
python3 scripts/check_docs.py
git diff --check
UV_CACHE_DIR=/tmp/mynews-v15-uv-cache uv run ruff check .
UV_CACHE_DIR=/tmp/mynews-v15-uv-cache uv run mypy src
UV_CACHE_DIR=/tmp/mynews-v15-uv-cache uv run pytest -q
```

来源包须显式安装到隔离环境后验证 `plugin list` 不执行工厂、每个
`plugin probe --plugin <id>` 独立运行。扩展脚本通过 Fake uv/参数透传测试；真实组合
采集不得调用固定项目根目录的脚本，而应在临时工作目录直接调用已准备环境中的
`mynews` 可执行文件，并展开计划内的 15 个 `--with-plugin`：

```bash
mynews collect --days 7 --with-plugin <逐项展开计划内 15 个插件 ID>
mynews validate --run output/latest.json
mynews digest --run output/latest.json --out-dir output --no-codex
```

最终 PASS 必须证明：默认采集仍能收集原有来源；扩展采集在同一 RunReport 中同时
记录原有来源与 15 个插件来源；任何失败都结构化可见且不破坏历史、latest、dedup 或
pending。真实 Codex 和 launchd 未执行时分别保持 SKIPPED/BLOCKED，不能借来源 probe
结果上调其状态。
