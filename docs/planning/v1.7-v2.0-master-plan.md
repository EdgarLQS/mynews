# mynews v1.7 收口至 v2.0 统一开发总计划

## 文档定位

本文是仓库唯一 Current 实施计划，统一管理 v1.7 P5 真实收口、v1.8 内部架构收敛、
v1.9 情报质量评估、v1.10 运行可靠性和 v2.0 编辑决策辅助。原 v1.7 Current 计划、
P5 插件分发准备计划和 v1.8-v2.0 Draft 路线图已归档；历史文档只用于追溯，不再决定
当前实施顺序。

本计划采用“一份总计划、阶段独立分支”的交付方式。每个阶段必须从包含上一阶段交付的
最新本地 `main` 创建分支，完成只读首验、独立修复和完整复验后先合入本地 `main`；
不得从已完成阶段分支继续开发，不自动 push。

规划基线为 2026-08-23 的 `main@003db29`，当时与 `origin/main` 同步且工作树干净。
开始任一后续阶段时必须重新记录最新 `main`，不得把本提交号永久当作未来实施基线。

## 跨阶段不变量

- discovery、Candidate、人工清单、媒体和模型输出不能直接产生 `verified`；只有程序复核后的
  第一方证据可以进入 Digest `main_items` 和正式情报。
- DedupState 与 PendingVerificationState 保持独立；SourcePlugin 只负责来源，不接触 Store、
  Verifier、Codex 或修改 `verified`。
- Digest 只读取已保存 RunReport 和上一期 Digest；failed run 不覆盖 latest，自动化报告成功
  后才能推进成功状态。
- publication ledger 与 weekly feedback 只记录作者明确提供的本地事实，不自动发布、不被
  分时任务或编辑建议自动修改。
- 默认保持现有 CLI、RunReport 1.x、Candidate v1、Digest 1.0、automation state 和插件选择
  语义兼容；新增能力使用独立 1.0 Schema。
- 离线门禁最高证明 Implemented；真实网络、生产 Codex、恢复、调度和作者使用必须分别取证
  后才能写 Verified。
- 不加入 Web UI、SQLite、自动发布、PPT、小红书、Canva、TTS、视频或无覆盖缺口的新来源。

## M1：重新冻结 P5 并收口 v1.7

### 授权与隔离

批准或实施本总计划不等于授权真实 P5。只有用户再次明确要求“开始 P5 真实验收”后，才允许
执行真实网络 probe、注册或启用 Scheduled Task、执行故障恢复演练。未经该授权，M1 保持
`SKIPPED`，M2 不得启动。

授权后从包含 M0 的最新 `main` 创建全新 detached worktree，不复用旧验收目录。所有 venv、
uv、Ruff、Mypy 和 Python 字节码缓存固定在 `logs/p5/runtime/`；运行前后校验源码、文档、Git、
publication ledger 和 weekly feedback 不变，且 `output/`、`state/`、`logs/` 之外没有运行残留。

### 执行顺序

1. 重新构建插件 wheel，记录版本、SHA-256 和 15 个 entry-point；只安装到隔离 venv。
2. 逐一执行 15 个插件真实 probe；`paperswithcode-daily` 保持 `manual/blocked`，discovery 只产生线索。
3. 回归默认 built-in、`--plugin` plugin-only、`--with-plugin` 追加和扩展采集脚本。
4. 按固定顺序彩排 `prepare --refresh`、扩展采集、`validate --check-evidence`、`digest`、分时报告。
5. 从健康 primary/research/incident 来源选择最新可访问的第一方条目完成真实 G6-V；没有合格
   候选时记 `BLOCKED`，不得用 fixture、搜索摘要或其他来源代替。
6. 彩排通过后，通过 Codex 应用创建一个项目级任务，严格复用根目录 `news-task.md`，观察真实
   09:00、18:00、跨两档 latest-only、前置失败、状态写入阻断和恢复运行。

只有所有场景通过且无必需门禁跳过，M1 才能 PASS。PASS 后用
`codex/v1.7-p5-verification` 仅回写 AI-02、DATA-07、OPS-04 和一致的计划/索引状态；
任务默认暂停。程序错误使用 `codex/v1.7-p5-fix` 修复并完整复验。

## M2：v1.8-A CLI 薄化

建立深 `ApplicationRuntime` module，主要 interface 固定为：

```text
run(Command) -> CommandOutcome
```

module 隐藏插件选择、Registry 扩展、Store、Verifier、DigestStore、时钟和用例装配；CLI 只负责
参数解析、中文呈现和退出码。保留现有 `main(argv, registry, store)` 测试注入、全部命令参数、
JSON、退出码和默认/plugin-only/追加选择语义。完成时必须删除 CLI 中的具体 Store、Codex、
插件和流水线装配；只增加一层浅包装而保留原装配不算完成。

## M3：v1.8-B 文件提交深 module

建立 `ArtifactCommitter.commit(writes)` interface，统一同目录 staging、`fsync`、替换、回滚和
临时文件清理。单文件使用一个 write；Prepare、NewsStore、DigestStore 使用批次；自动化报告
和状态使用两次有序提交保留“报告先于状态”。统一内部 `ArtifactCommitError`，保留失败阶段、
目标路径和回滚结果，再由调用方映射为既有用户错误。

完成时删除 Report、Watchlist、Validation、Editorial IO、Prepare、NewsStore 和 DigestStore 中
重复的 `NamedTemporaryFile`、`os.replace` 与回滚实现。不承诺跨文件系统事务，不改变 latest
推进、历史保护或业务提交集合。

## M4：v1.9 情报质量评估

新增：

```text
mynews evaluate --suite <suite.json> --out-dir <目录>
```

建立 `QualityEvaluator.evaluate()` 和独立 `QualityEvaluation 1.0` Schema，原子生成 JSON 与
中文 Markdown。首版固定样本至少 24 个案例，官方直达、discovery、重试失败、多来源同事件、
相似不同事件、价格变化、提示注入、证据漂移八类各三例。

分别报告候选覆盖、verified 错误升级、误合并/漏合并、pending 演进、主榜/线索污染和排序
稳定性，不输出综合分。verified 错误升级、主榜污染和不安全事件合并为零容忍，任一期望不符
退出 1。离线样本通过最高为 Implemented；Verified 需至少 20 个真实事件、覆盖七天和三类
来源角色的人工标注验收。

## M5：v1.10 运行可靠性

新增：

```text
mynews ops diagnose --root <目录> --days 30 --out-dir <目录>
mynews ops retention-plan --root <目录> --older-than-days <N> --out-dir <目录>
mynews ops recovery-check --source-root <目录> --target <全新空目录> --out-dir <目录>
```

诊断区分来源、网络、Codex、证据、存储和调度失败，并显示最后成功档位、连续失败、陈旧 latest
和 pending。保留计划只列候选，不移动或删除文件；人工台账、latest 指向对象和仍被引用的历史
记录始终受保护。恢复检查只复制白名单数据到全新空目录，校验哈希、Schema、相对引用、latest/
历史、dedup、pending 和 automation state，禁止原地恢复和覆盖。

报告只含相对路径、哈希和统计，不回显正文或秘密。真实隔离恢复演练通过后才能标记 Verified；
没有真实演练时最高为 Implemented。

## M6：v2.0-A 共享结构化 Codex 进程 Adapter

v2.0 将成为第三个 Codex 调用方，因此正式触发共享进程 Adapter。Adapter 只统一临时目录、
Schema 文件、CLI 参数、超时、返回码和输出读取；Verifier、Digest 和编辑建议继续分别拥有
prompt、响应模型、程序复核和安全回退。完成时删除核验与 Digest 中重复的 subprocess 和临时
目录实现，兼容门禁全部通过后再进入 M7。

## M7：v2.0-B 编辑决策辅助

新增：

```text
mynews editorial review \
  --week YYYY-Www \
  --out-dir output/editorial/reviews \
  [--no-codex]
```

只读 Candidate、Digest、publication ledger 和 weekly feedback，生成独立 `EditorialReview 1.0`
JSON 与 Markdown。输出确定性统计、已发布/未发布/待核查分层、重复选题提示、实质更新提示和
最多五条建议；每条建议必须包含可解析的事件或指标引用。

至少积累四个完整 ISO 周、十条 publication 记录和对应反馈后才生成趋势与模型建议；不足时
输出 `partial` 和缺失原因。Codex 默认可用但不是事实来源；`--no-codex` 仍生成完整确定性报告。
Codex 失败或返回未知引用时丢弃建议、保留统计并退出 3。周报告原子更新 `<week>.json/md` 和
latest，失败不覆盖旧分析，且不回写任何输入或自动发布。

## 公共 interface 与兼容

- 新命令沿用退出码：0 成功、1 数据/程序失败、2 参数错误、3 partial/警告。
- QualityEvaluation、Operations、EditorialReview 使用独立 1.0 Schema；不修改 RunReport 1.x、
  Candidate v1、Digest 1.0 或 automation state。
- built-in、`--plugin` 和 `--with-plugin` 语义不变；不新增生产依赖。
- 若实施必须改变 Accepted ADR，立即停止该阶段，先新增替代 ADR；不得直接改写原决定。

## 每阶段统一验收

每个分支执行“只读首验 -> 独立修复 -> 完整复验”，至少运行：

```bash
python3 scripts/check_docs.py
git diff --check
uv run ruff check .
uv run mypy src
uv run pytest -q
uv run mynews --help
```

并按范围增加 interface、CLI、Schema、失败注入、隐私、原子恢复和真实环境门禁。未执行项写
`SKIPPED`，外部阻断写 `BLOCKED`，程序问题写 `FAIL`。阶段通过后先合入本地 `main`，不自动
push；下一阶段只能从新的 `main` HEAD 创建分支。
